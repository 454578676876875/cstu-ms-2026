--- Act: read vote/app.py, worker/Program.cs (skim), result/server.js (skim) ---
vote/app.py is a small Flask app: GET / renders a form (already-voted cookie -> pre-selects the
option), POST / writes {vote, voter_id} as JSON into a Redis list. worker reads that list,
looks up (voter_id) in Postgres, and inserts/updates a row in the votes table. result/server.js
subscribes to Postgres NOTIFY on the votes table and pushes live tallies to the browser over
Socket.IO.

--- Observe / synthesize ---
Plain-English summary:

  This is a 3-tier, polyglot microservice demo of the "vote flows through a queue into a
  database, then out to a live dashboard" pattern. A user hits the vote service (Python) and
  picks cat or dog; that vote is pushed onto a Redis list rather than written straight to the
  database, which decouples the front door from storage load. A separate worker (.NET) drains
  that queue and upserts each vote into Postgres, keyed by voter, so re-voting changes your
  vote instead of adding a duplicate. A third service, result (Node.js), listens for Postgres
  change notifications and streams live updated tallies to a results page over a websocket, so
  the results page updates without polling. Redis and Postgres each expose a healthcheck the
  Compose file uses to gate service startup order. worker won't start until both redis and db
  report healthy, so it can't come up and immediately fail its first connection attempt.
